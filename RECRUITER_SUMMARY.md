# Data Quality Copilot — NYC Taxi · two-minute summary

Every figure below comes from `reports/` and is regenerated by `scripts/reproduce.sh`.

**1. Business question.** How can a data team detect, isolate, explain and monitor data-quality problems *before* unreliable records reach analytics?

**2. Problem.** Monthly NYC taxi files arrive with negative fares, trips dated 2002, 398,608-mile distances, new columns and vendor-specific conventions. Nothing stops them, so they flow silently into revenue reports and models.

**3. Dataset.** Official NYC TLC Yellow Taxi trip records, November 2024 – February 2025: 4 parquet files, 14,367,509 trips. Real data only; each file is registered with its SHA-256.

**4. Architecture.** Immutable raw layer → schema contract → PostgreSQL landing → 23 versioned rules (Polars) → quarantine or curated layer (dbt) → drift detection, anomaly detection and two ML models as a second line → FastAPI, Prometheus, Grafana, Streamlit. Orchestrated with Prefect, containerised with Docker, with a GitHub Actions workflow that runs the tests and a quality gate.

**5. Main data-engineering challenge.** Making the pipeline safe to re-run and impossible to lose data in. Raw loads are skipped when the file hash is already loaded, quarantine is an upsert that never deletes, and dbt asserts on every build that `raw = clean + quarantined`. A full second run produced identical results and zero duplicated rows.

**6. Important design decision.** Explicit rules decide what is quarantined; statistics and ML only raise questions. A rule is explainable and stable; an anomaly detector flags what is rare, not what is wrong.

**7. Measured result.** 489,224 records quarantined (3.41%), none lost. On labelled errors, rules plus the fare model reach precision 0.96 and recall 0.75; Isolation Forest alone reaches 0.10 and 0.05. The platform also caught a real schema change, a 19.7% drop in trip duration after congestion pricing, and a quality regression that breaches the SLO in January and February 2025 — reported, not hidden.

**8. Failure encountered.** The first "total = sum of components" rule flagged 28% of rows. The cause was not bad data: one vendor reports surcharges inside another column. The rule went through three versions and now flags 0.15–1.07%.

**9. Trade-off.** Records with a warning (for example a missing passenger count) stay in the curated data, flagged. Quarantining them would discard 9–23% of trips whose fares are valid.

**10. What would change at enterprise scale.** Object storage and a lakehouse format instead of loading raw rows into PostgreSQL (the slowest stage); a managed secret store and TLS; scheduled backups with point-in-time recovery; schema migrations; alert routing to an on-call rotation; and partitions processed in parallel instead of one after another on a single machine. The current gaps are listed category by category in [PRODUCTION_READINESS.md](PRODUCTION_READINESS.md).
